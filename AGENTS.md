# Правила работы над JavaPlay

## Назначение и приоритеты

Создаём полноценную 2D браузерную игру для изучения Java, а не учебник с декоративной картой.
Перед изменениями прочитай README.md, docs/00-agent-context.md и относящиеся к задаче документы в docs/.

Приоритеты: качество обучения → интерес игрока → простота понимания → настоящая практика → техническая корректность → красота → количество контента.
Новые явные указания пользователя имеют приоритет над этими правилами.

## Проверка и тестирование — обязательные ограничения

1. **Не использовать браузер для проверки проекта.** Не открывать игру для собственной проверки, не запускать Playwright, Cypress, Selenium, browser automation, headless-браузеры и не снимать браузерные скриншоты для QA.
2. **Пользователь сам проверяет и тестирует игру.** Агент готовит изменения, инструкции запуска и конкретные сценарии ручной приёмки с ожидаемым результатом.
3. **Не писать юнит-тесты сейчас.** Не создавать тестовые файлы, фикстуры, test runner или зависимости ради юнит-тестов. Напишем их позже по отдельному запросу пользователя.
4. Не добавлять другие автоматические тестовые наборы вместо отложенных юнит-тестов. Не запускать тесты самостоятельно без нового указания пользователя.
5. Разрешены чтение кода, проверка diff, компиляция/сборка, проверка типов, линтер и статическая проверка схем. До запуска команды убедись, что она не запускает тесты или браузер скрыто.
6. Не заявлять «проверено в браузере», «тесты прошли» или «всё работает», если этого не делали. Отдельно сообщать результаты статических проверок и статус пользовательской приёмки.
7. Не считать отсутствие ответа успешной приёмкой. Зависимый этап, требующий рабочего результата предыдущего, продолжать после подтверждения пользователя или его явного указания продолжить без приёмки. Независимые документационные работы можно продолжать.
8. Эти ограничения не удаляют из продукта проверку решений ученика, кнопку проверки задания и будущие учебные темы JUnit/Mockito/Testcontainers. Их реализация следует дорожной карте; тесты самого репозитория остаются отложенными.

## Рабочий процесс

- Общаться и писать учебные материалы на русском; идентификаторы кода — на английском.
- Менять небольшие логически законченные части. Не реализовывать весь курс одним проходом.
- Перед работой назвать цель и ожидаемый результат. После — перечислить изменённые файлы, объяснить запуск, результат и сценарии для пользователя.
- Вносить полный рабочий код в файлы; не оставлять заглушки вместо заявленной функциональности. Для объёмных изменений достаточно ссылок на файлы в ответе; полный текст показывать по запросу пользователя.
- Обновлять план, если меняются границы, зависимости или решения. Различать «запланировано», «реализовано», «проверено статически», «принято пользователем».
- Поддерживать контекст-менеджмент: при изменении статуса, границ этапа, следующего шага или карты чтения обновлять docs/00-agent-context.md; подробные результаты и handoff записывать в docs/06-agent-worklog.md.
- Не менять несвязанные файлы и не откатывать чужие изменения. Не добавлять новые зависимости без объяснимой необходимости.
- Не создавать агентов только из-за перечисленных в исходном промпте профессиональных ролей: это разные аспекты проектирования, а не требование параллельного исполнения.

## Архитектура

- React управляет интерфейсом; Phaser — миром и анимацией. Обмен идёт через типизированные события, не через взаимное изменение внутренних объектов.
- Учебный контент хранить отдельно от движка, со стабильными ID, версиями и явными prerequisites.
- Симулятор и реальная Java работают через общий ExecutionProvider. Симулятор не выдавать за JVM; явно показывать его ограничения игроку.
- Не запускать недоверенный Java-код на машине приложения или пользователя без предусмотренной изоляции. Не использовать eval для обработки решений.
- Авторитетное состояние, награды и проверку решения отделять от визуального воспроизведения. Повторный ответ не должен повторно начислять XP.
- Не доверять событиям и stdout ученического кода: проверять схему, права на объект, лимиты и допустимость эффекта для конкретного задания.
- Секреты не хранить в репозитории. Не добавлять открытую удалённую JVM до реализации изоляции и ограничений из архитектурного документа.
- Фиксировать версии инструментов при реализации; не использовать плавающие latest. Совместимость стека в документах пока является предположением, а не выполненной проверкой.

## Обучение и игровой дизайн

- Каждое новое понятие: простое объяснение → аналогия → визуальная метафора → корректный Java-код → применение.
- Учебный цикл: объяснение → пример → малая практика → игровая задача → самостоятельное применение → закрепление.
- Ориентир: 20–30% объяснений, 70–80% практики и взаимодействий.
- Не требовать синтаксис или понятия, которые ещё не были введены. Ранний main можно дать готовым шаблоном и объяснять постепенно.
- Сначала проблема в мире, затем выбор инструмента. Код должен заметно влиять на игровой мир.
- Для задания нужны цель, prerequisites, критерии успеха, визуальный результат, три подсказки и награда.
- Ошибки объяснять спокойно: что произошло, где, почему и какой следующий шаг. Сохранять доступ к оригинальному сообщению Java.
- Аналогии сопровождать границами применимости. Не называть String примитивом, volatile заменой атомарности или симулятор настоящей Java.
- Spring вводить после уверенной базы Java. Устаревшие API показывать с контекстом и современными альтернативами.
- Короткие диалоги, взрослый уважительный тон, умеренный юмор. Не использовать длинные лекции, фарм однотипных задач и обязательные ежедневные серии.

## Критерий завершения изменения

Изменение находится в пределах этапа, описано в документации, допустимые статические проверки выполнены либо объяснено, почему они недоступны; пользователь получил инструкцию ручной проверки. Статус «принято» ставится только после его подтверждения.
