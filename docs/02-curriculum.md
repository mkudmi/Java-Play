# Образовательная карта Java Zero → Java Pro

## Методика и критерий освоения

Одна учебная единица вводит одну основную новую идею. Ориентир длительности — 5–15 минут, без таймера, ограничивающего ученика. Изучение полного курса не гарантирует профессиональную квалификацию автоматически: результат подтверждается самостоятельными проектами и переносом знаний в локальную среду разработки.

Шаблон единицы: проблема мира → объяснение простыми словами → бытовая аналогия и её границы → визуальный пример → Java → малая практика → самостоятельная задача → повторение в другом контексте.

Перед публикацией автор отвечает на шесть вопросов:

1. Какое конкретное знание получает игрок?
2. Зачем оно ему в задаче и в обычной разработке?
3. Что он делает руками?
4. Как результат меняет мир?
5. Какие старые знания он применяет?
6. Может ли он применить понятие самостоятельно после задания?

Если ответ отсутствует, урок требует переработки. Для первого урока отсутствие старых знаний допустимо и указывается явно.

Карточка урока содержит ID и версию, тему, prerequisites, цель, диалог, уровни объяснения, пример, starter code, разрешённый API, исходное состояние мира, правила проверки, ожидаемые классы ошибок, три подсказки, награду и перенос навыка. Авторское решение хранится отдельно от клиентского контента, когда появится серверная проверка.

Аналогии: переменная — подписанная ячейка (ссылка не содержит сам объект); метод — устройство с входами и результатом (есть и побочные эффекты); класс — чертёж, объект — экземпляр; массив — фиксированные пронумерованные ячейки; List — последовательность изменяемого размера; интерфейс — договор; исключение — сигнал сбоя; поток — работник (параллельность не гарантируется). Точная модель постепенно уточняет простую.

Stack изучается для чтения существующего кода с сопоставлением с Deque; StringBuffer — с объяснением контекста, а не как стандартный выбор для любой строки. Нативную Java-десериализацию недоверенных данных не использовать как рекомендуемый способ хранения. Для денежных расчётов на продвинутом этапе вводить BigDecimal, не закреплять double как правильную финансовую модель.

Skill Tree отражает зависимости таблицы: после ООП ветви строк, исключений и коллекций частично параллельны; файлы и functional Java сходятся в дальнейших проектах. Spring закрыт до самостоятельного Java-проекта. Темы памяти вводятся простыми моделями раньше C15, но глубокая работа с JVM остаётся поздней.

## 20 примеров заданий

| № | Проблема и действие игрока | Навык / формат | Наблюдаемый результат и критерий |
|---|---|---|---|
| 1 | Маяк молчит: дописать сообщение в готовом main | println; дописать код | Нужная строка появляется в stdout, маяк отвечает |
| 2 | У парома пуст индикатор: задать запас топлива | int; малая практика | Индикатор показывает вычисленное значение |
| 3 | Рассчитать остаток топлива после маршрута | Арифметика; предсказать и написать | Транспорт доезжает, остаток соответствует расходу |
| 4 | Табло обращается к неизвестной переменной: исправить имя | Область видимости/диагностика; исправить баг | Ошибка исчезает, табло обновляется |
| 5 | Ворота должны пропускать только с пропуском | if и boolean; самостоятельный код | С пропуском открыто, без пропуска закрыто |
| 6 | Диспетчер направляет посылки по категории | switch; выбор конструкции | Все категории и неизвестная категория обработаны |
| 7 | Робот вручную проверяет пять кристаллов | for; автоматизация | Ровно пять разных кристаллов проверены |
| 8 | Патруль застрял в бесконечном обходе | while; найти и исправить баг | Обход завершается при условии, лимит не превышен |
| 9 | Неверный индекс гасит последний маяк | Массив; отладка | Все элементы обработаны, нет выхода за границы |
| 10 | Перед запуском двигателя перепутаны операции | Методы; собрать код | Инициализация, проверка и запуск идут в допустимом порядке |
| 11 | Система защиты должна сама выбрать цели и рассчитать урон | Массивы, условия, циклы, методы; босс | Система проходит несколько сценариев без указания конструкций |
| 12 | Магазин копирует логику каждого товара | ООП/композиция; рефакторинг | Поведение сохранено, новый товар добавляется без копирования логики |
| 13 | Архив выдаёт дубликаты пропусков | Set/Map; выбор структуры | Уникальные пропуска, поиск по ID; игрок объясняет выбор |
| 14 | Разные склады принимают несовместимые грузы | Generics и PECS; самостоятельный код | Допустимые типы принимаются, ошибки типов диагностируются компилятором |
| 15 | Повреждённый файл обрушает весь архив | Files/исключения; восстановление | Корректные записи прочитаны, ошибка сообщена, ресурс закрыт |
| 16 | Торговый совет просит сводку заказов по районам | Streams/collectors; обработка данных | Итоги совпадают с данными, пустой набор обработан |
| 17 | Два робота продают последний билет одновременно | Concurrency; расследование race condition | В управляемом конкурентном сценарии продан один билет, данные согласованы |
| 18 | Мастерская замедляется после каждого посетителя | JVM/profiling; анализ | Найдена причина удержания объектов, улучшение подтверждено измерением |
| 19 | API магазина списывает деньги, но не выдаёт товар | REST/SQL/транзакции; code review и исправление | Операция атомарна, повтор запроса не создаёт вторую покупку |
| 20 | Город ждёт полноценную систему сервисов | Spring Boot/PostgreSQL/auth/tests/Docker; финальный проект | Магазин, склад и транспорт используют API; ошибки и восстановление видны в мире |

У каждого задания есть три подсказки и награда согласно GDD. Структурные качества рефакторинга, архитектуры и профилирования не сводить к единственному выводу: нужны рубрика, объяснение ученика и ручное ревью на соответствующем этапе продукта.

## Финальный проект и переход к самостоятельной работе

Игрок создаёт backend города: REST API, Spring Boot, PostgreSQL, аутентификация и права доступа, слои controller/service/repository, валидация, обработка исключений, транзакции, конкурентный сценарий, журналирование, конфигурация, учебные тесты и Docker. Части мира выступают клиентами API.

Результат включает Git-репозиторий, инструкции запуска, схему данных, описание API, объяснение архитектурных решений и исправление нескольких заранее подготовленных дефектов. Последнее задание даётся как техническое задание без готового решения. Дополнительный feature request проверяет перенос навыка.

Учебные тесты в C20 относятся к будущему содержимому игры. По текущему указанию пользователя юнит-тесты приложения сейчас не создаются.
