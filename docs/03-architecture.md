# Техническая архитектура

## Решения и границы достоверности

Это целевая архитектура и предлагаемый стек, не отчёт о проверке совместимости. Точные версии зависимостей и JDK фиксируются на этапе настройки по поддерживаемому сочетанию; не выбирать latest автоматически. Браузерная проверка агентом исключена.

### Зафиксировано при реализации M0 (2026-09-08)

Node.js 25.6.0 и npm 11.8.0 соответствуют установленному рабочему окружению; это фиксация окружения разработки, не выбор серверного LTS. Версии закреплены в `.nvmrc`, `engines` и `packageManager`, точные зависимости — в package.json и package-lock.json.

Клиент: React/React DOM 19.2.8, TypeScript 5.9.3, Vite 7.3.6, React plugin 5.2.0, Phaser 3.90.0, Monaco 0.56.0. Линтер: ESLint 10.10.0, typescript-eslint 8.56.0 и React Hooks plugin 7.1.1. Для Vite/React plugin требования к Node получены из npm registry; выбранное окружение входит в их разрешённый диапазон. Это не подтверждает визуальное поведение в браузере.

Используются npm workspaces и один lockfile. Phaser и Monaco загружаются отдельными динамическими импортами; Monaco и worker поставляются из локальной сборки, без CDN. React StrictMode включён; компоненты освобождают scene/editor/model при размонтировании. На M0 есть только пакет contracts; content-schema/simulator создаются по мере появления использующего их кода. Через npm overrides фиксируются DOMPurify 3.4.15 и esbuild 0.28.2, чтобы исключить обнаруженные npm audit уязвимые транзитивные версии. Общий store понадобится с игровой логикой; состояние открытой панели пока локально в React.

Известная особенность диагностики зависимостей: `npm ls dompurify` в этом workspace возвращает `ELSPROBLEMS`, сравнивая установленную 3.4.15 с исходной точной зависимостью Monaco 3.4.8, несмотря на корневой override. Чистая `npm ci` воспроизводит исправленную версию и проходит с 0 известными уязвимостями. Не откатывать DOMPurify на 3.4.8 ради устранения этого сообщения; override пересмотреть при обновлении Monaco.

|---|---|---|
| Клиент | TypeScript, React, Vite | Типизированные контракты и отдельные панели интерфейса |
| Мир | Phaser 3 | Сцены, камера, ввод, коллизии и анимация отделены от учебного UI |
| Редактор | Monaco Editor | Редактирование кода и diagnostics; Java autocomplete ограничим учебным API |
| UI | CSS с токенами, без тяжёлого UI-фреймворка на старте | Меньше зависимостей и контроль читаемости |
| Состояние | Небольшой централизованный store и reducer; адаптер событий Phaser | Один источник состояния, предсказуемые переходы |
| Контент | Версионированные JSON-данные, runtime-валидация схем | Новые задания без изменения движка |
| MVP execution | Ограниченный parser/interpreter в Web Worker | Локальный цикл без инфраструктуры; изолирован от основного UI-потока |
| Будущий backend | Java + Spring Boot, модульный монолит; Maven | Предметная область совпадает с курсом, достаточно для первого сервера |
| Хранение | MVP: IndexedDB; сервер: PostgreSQL | Сначала локальное сохранение, затем транзакции и синхронизация |
| Очередь | Сначала PostgreSQL jobs с lease; отдельный dispatcher | Не нужен отдельный брокер до появления измеренной нагрузки |
| Worker | Отдельный сервис управления одноразовыми sandbox | Недоверенный код отделён от API и БД |

Для серверного JDK первоначально рассмотреть Java 21 или более новую поддерживаемую LTS; окончательное решение фиксировать перед реализацией исполнителя. Учебный language level — явное свойство контента. Preview-возможности не включать по умолчанию.

## Модули и взаимодействия

React UI → application commands → quest engine → ExecutionProvider → нормализованный результат → evaluator → attempt world → фиксация progression/save → Phaser playback.

- Phaser отвечает за движение, близость к NPC, коллизии, камеру, эффекты. Он отправляет намерения и получает снимки/события.
- Quest engine управляет prerequisites и состояниями `locked → available → active → completed`.
- Попытка имеет состояния `idle → running → evaluated`, отдельно `cancelled`, `execution-error`, `infrastructure-error`.
- Progression service начисляет награды идемпотентно по quest completion ID.
- Content loader проверяет схемы, ссылки, уникальность ID и отсутствие циклов зависимостей.
- UI подписан на публичное состояние; не хранит вторую независимую копию XP или статуса задания.

## Контракт выполнения

Запрос ExecutionRequest содержит `requestId`, `questId`, `questVersion`, `source`, `languageLevel`, `mode` (run/check), `initialWorld`, `seed`. Для серверного исполнения мир и правила подставляет сервер по ID; клиентский снимок не считается доверенным.

Ответ ExecutionResult содержит `requestId`, `provider` (simulator/java), `status`, `stdout`, `stderr`, `diagnostics`, `events`, `metrics`. Диагностика содержит код, исходное сообщение, русское пояснение и диапазон строки/столбца в редакторе. Событие содержит sequence, разрешённый type, targetId и ограниченный payload.

Ошибки компиляции, runtime, неподдерживаемый синтаксис, timeout, отмена и сбой инфраструктуры различаются. При последнем знания не оцениваются. Отмена — отдельная операция провайдера; результат старого requestId не изменяет текущую попытку.

Evaluator получает результат и правила задания. «Запустить» показывает наблюдаемый сценарий; «Проверить» запускает предусмотренные варианты входных данных и сравнивает инварианты. Это игровая функциональность. В MVP достаточно одного сценария для каждого линейного задания; интерфейс заранее допускает несколько.

## Ограниченный симулятор MVP

Поддержать только явно описанное подмножество: готовая оболочка `public class Main`/`main`, объявления int и String, присваивание, целочисленные литералы, строки, `+`, `-`, `*`, скобки, `System.out.println`, разрешённый вызов `beacon.signal(int)`, комментарии. Остальное отклонять понятной диагностикой. Для MVP не нужны циклы, объекты, импорты, файловые операции и сеть.

Использовать tokenizer → parser → AST → evaluator с таблицей символов. Не подменять вычисление регулярными выражениями, совпадением с образцом, JavaScript eval или Function. Для поддержанных операций определить семантику Java, включая int и конкатенацию; если точная семантика ещё не реализована, сузить допустимый язык и объяснить ограничение.

Лимиты: длина исходника, число AST-узлов, глубина выражений, число шагов, размер вывода и событий. Выполнение в Worker, с возможностью terminate по wall-clock timeout. Конкретные значения задаются конфигурацией и отображаются в инструкциях.

Интерфейс явно пишет «Учебный симулятор: поддерживается ограниченный Java-синтаксис». Его ошибки не маркируются как реальные сообщения javac. Перед расширением к ООП подключить JVM; не строить собственную полную Java VM.

## Безопасное выполнение настоящей Java — после MVP

1. API проверяет пользователя/анонимную сессию, квоту, длину исходника и доступ к заданию; создаёт job.
2. Dispatcher арендует job и передаёт выделенному worker. Повторы имеют request ID, lease и ограничение попыток.
3. Worker создаёт отдельную одноразовую среду без секретов, доступа к API-хосту и рабочей БД.
4. Внутри ограниченной среды выполняются и javac, и java. Компиляция тоже обрабатывает недоверенный ввод.
5. Собираются ограниченные stdout/stderr и события; результат проходит внешнюю проверку схемы и инвариантов.
6. После завершения/отмены/timeout уничтожается вся группа процессов и временные данные. Сервер фиксирует результат и награду транзакционно.

Предварительный профиль для коротких задач: 1 CPU, 256 MiB RAM, 64 процесса, 10 секунд компиляции, 3 секунды выполнения, 64 KiB вывода, 1 000 событий. Это стартовые гипотезы: JVM и компилятор могут потребовать больше памяти, поэтому пользователь вручную проверяет профиль на этапе интеграции. Ошибка профиля не считается ошибкой ученика.

Обязательные ограничения: сеть отключена, непривилегированный UID, read-only root filesystem, отдельный ограниченный tmpfs, cap-drop ALL, no-new-privileges, seccomp и доступный LSM-профиль, cgroups CPU/RAM/pids, ограничение файлов и размера вывода. Не монтировать домашнюю директорию, исходники сервера, Docker socket или секреты внутрь sandbox. Управляющий worker имеет минимальный доступ и живёт отдельно от API.

Docker — упаковка и часть ограничения, но не достаточная самостоятельная граница для публичного исполнения враждебного кода. Перед публичным запуском нужен усиленный runtime (например, gVisor или microVM), изолированные worker-узлы и отдельная приёмка безопасности. До этого реальная JVM доступна только в контролируемом окружении; публичный endpoint не выпускается.

События Java API не считаются доказательством корректности: ученик потенциально может подделать stdout. Отдельный канал событий, allowlist целей, лимиты, проверка столкновений/границ и независимое вычисление ожидаемого состояния обязательны. Когда важна именно конструкция языка, использовать структурный анализ, а не доверять команде «квест завершён» из кода ученика.

Будущие backend-проекты требуют отдельного профиля: ограниченная сеть только внутри одноразового учебного окружения, временная PostgreSQL, выделенный срок жизни, проксирование разрешённых запросов и полная очистка. Не ослаблять сетевой запрет профиля обычных Java-задач ради Spring-проектов.

## Данные и сохранения

MVP сохраняет в IndexedDB: save schema version, content version, локальный profile ID, позицию героя, завершённые квесты, XP, навыки, достижения, черновики по quest ID, подсказки и постоянные изменения мира. Запись завершения и награды атомарная. Черновики сохраняются с debounce и при закрытии панели. При недоступном хранилище показывается честное предупреждение; игра не обещает сохранение.

Предусмотреть экспорт/импорт JSON, валидацию импорта, миграции и резервную копию перед миграцией. Не перезаписывать неизвестную более новую версию сохранения. Локальный прогресс редактируем пользователем и не является защищённым рейтингом.

Будущая схема PostgreSQL:

| Таблица | Основные поля и ограничения |
|---|---|
| users | id, auth_subject unique, display_name, created_at; без обязательной даты рождения |
| profiles | id, user_id FK, settings, content_version, revision |
| quest_completions | profile_id FK, quest_id, quest_version, completed_at; unique(profile_id, quest_id) для базовой награды |
| attempts | id, profile_id FK, quest_id/version, provider, status, hint_level, created_at; политика срока хранения исходников |
| execution_jobs | id, attempt_id FK, request_id unique, state, lease_until, worker_id, retry_count, result_ref |
| reward_ledger | id, profile_id FK, completion_id FK, kind, amount; unique(completion_id, kind) |
| skill_progress | profile_id FK, skill_id, mastery_state, independent_successes, next_review_at; составной PK |
| achievement_unlocks | profile_id FK, achievement_id, unlocked_at; составной PK |
| inventory_items | profile_id FK, item_id, quantity; составной PK, quantity >= 0 |
| world_state | profile_id FK, region_id, state_json, revision; составной PK |
| code_drafts | profile_id FK, quest_id, content_version, source, updated_at; составной PK |

Контент заданий живёт в версионированных файлах; в БД хранится привязка к версии, не дублирующий редактор курса. Позже локальный прогресс импортируется явно; конфликты устройств решаются версией и журналом завершений, а не безусловным last-write-wins для XP. Исходники не отправляются в аналитику; хранение серверных попыток ограничивается необходимым сроком.

## Решения, которые защищают от переделки

- Стабильные ID и миграции сохранений: правка текста не обнуляет прогресс.
- ExecutionProvider и единый результат: подключение JVM не меняет интерфейс квестов.
- Разделение preview/commit: ошибка и повтор не портят мир и награды.
- Отдельные данные контента: новый регион не требует копировать логику сцены.
- Разделение Phaser/React: фокус редактора и жизненный цикл сцены остаются управляемыми.
- Версия Java в задании: обновление runtime не меняет молча учебные примеры.
- Авторитетный evaluator и ledger на сервере: визуальные события не дают право на награду.
- Версионированные sandbox-профили: профессиональные проекты не расширяют права начальных задач.

## Реализация мира M1

Геометрия острова, деревьев, препятствий и NPC вынесена в `game/world/village.ts`. Движение проверяет опорный круг ног радиусом 9: восемь точек должны лежать на острове/причале, а круг не должен пересекать прямоугольные препятствия. Шаг разбивается на отрезки не длиннее 3 единиц с разрешением по осям; delta ограничен 50 ms после задержки кадра. Это небольшая кинематическая модель без отдельного физического движка.

`WorldInput` получает события только из сфокусированного контейнера React, использует физические коды клавиш и сбрасывает состояние при блокировке/потере фокуса. Phaser keyboard отключён, чтобы редактор не конфликтовал с глобальным захватом клавиш. React управляет блокировкой ввода и карточкой NPC; сцена сообщает о взаимодействии типизированным событием. В M1 нет состояния квестов. Фигуры и объекты сортируются по глубине, камера следует за героем в границах сцены.
