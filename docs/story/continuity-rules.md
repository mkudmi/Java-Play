# Continuity, Debugging, Legacy, Future Rules

## Debugging Storyline

| Stage | Debugging Form | Story Use |
|---|---|---|
| C01-C02 | Ошибка синтаксиса рядом с кодом | Игрок видит, что машина выполняет точно написанное. |
| C03-C04 | Неверное поведение механизма | Нужно найти неправильное условие или остановку цикла. |
| C05-C06 | Runtime error и область видимости | Ошибка становится событием мира, а не наказанием. |
| C08-C09 | Stack trace, исходное сообщение, try/catch | Ника учит читать след, сохранять причину и восстанавливаться. |
| C12-C13 | Логи, поврежденные строки, пустые результаты | Данные бывают плохими, отсутствующими и слишком большими. |
| C14-C15 | Нерегулярные падения, race condition, memory leak | Ошибка проявляется под нагрузкой и требует измерений. |
| C16-C20 | Debugger, production logs, review, tests | Игрок доказывает поведение и предотвращает повтор. |

## Legacy Evolution

Ранний код игрока не высмеивается. Он становится материалом роста: "тогда это было правильным уровнем решения; теперь мир стал больше". Поздние задания возвращают простые скрипты как legacy-модули, которые нужно документировать, покрывать учебными тестами, разделять на классы, переносить в сервисы или защищать транзакциями.

## Foreshadowing Map

| Early Hint | Later Meaning |
|---|---|
| В C01 маяк иногда пишет одинаковую строку дважды. | В C17-C18 это станет темой идемпотентности и транзакций. |
| В C02 счетчик уходит в отрицательное значение. | В C15 игрок поймет границы памяти и представления значений глубже. |
| В C04 робот проходит маршрут не всегда одинаково при двух командах. | В C14 это окажется первым следом общей гонки задач. |
| В C08 старый лог содержит `FINAL_FINAL_V2`. | В C20 это станет входом в legacy review без превращения мира в мем. |
| В C10 дубликаты пропусков выглядят бытовой ошибкой. | В C18-C20 это вырастет в модель identity, прав и безопасности. |

## Humor Guidelines

Юмор рождается из инженерной узнаваемости и человеческого характера: странные комментарии, осторожные обходы старого модуля, "на моей машине работает", спор Бора и Севера о том, когда уже пора проектировать. Юмор не должен превращать Java-концепции в персонажей вроде "Короля String" и не должен мешать серьезным ставкам.

## Tone Guidelines

Тон уважительный, приключенческий, теплый. Ребенку должно быть понятно, взрослому не неловко. Технологии объясняются простым языком, но не искажаются. Ошибки игрока — нормальная часть расследования.

## Things The Story Must Never Do

- Не использовать концепцию раньше `JAVA_LEARNING_ROADMAP.md`.
- Не отделять "урок Java" от события мира.
- Не делать злого хакера единственной причиной конфликта.
- Не называть `String` примитивом, `volatile` атомарностью или симулятор настоящей JVM.
- Не превращать Spring в магию.
- Не делать optional-квест единственным местом обязательного знания.
- Не стирать последствия кода после завершения задания.

## Story Development Rules For Future Content

RULE 1. Нельзя использовать учебную концепцию раньше ROADMAP.

RULE 2. Каждый обязательный урок должен иметь понятную мотивацию внутри мира.

RULE 3. Сначала возникает проблема, потом появляется новый инструмент Java.

RULE 4. Java должна изменять состояние игрового мира.

RULE 5. Старые знания должны регулярно возвращаться.

RULE 6. Новый материал не должен выглядеть как внезапная школьная лекция.

RULE 7. Игроку постепенно дают все меньше прямых указаний.

RULE 8. Масштаб ответственности растет вместе со знаниями.

RULE 9. Код игрока должен иметь долгосрочные последствия.

RULE 10. Финальное обучение и финальный сюжет являются одной и той же цепочкой событий.

RULE 11. Любой chapter должен отвечать: где игрок, кто просит помощи, почему это важно людям, что сломано, почему старых знаний мало, что меняется после решения.

RULE 12. Debugging должен эволюционировать от видимой ошибки к расследованию поведения под нагрузкой.

RULE 13. Legacy code показывается с уважением к контексту, а не как шутка над прошлым разработчиком.

RULE 14. Архитектурные решения должны иметь trade-off, а не единственно "правильную магическую форму".

RULE 15. Проверка решения в мире не должна полагаться только на совпадение текста кода с образцом.
